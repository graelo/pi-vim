# AGENTS.md

`@graelo/pi-vimmode` is a pi extension that replaces pi's prompt editor with a
Vim-style modal editor. It is a hard fork of `pekochan069/pi-vimmode` at v0.9.0
(see `docs/adr/0005-hard-fork-and-node-toolchain.md`). Product boundary:
practical prompt editing, not full Vim/Neovim parity.

## Commands

- `npm run check`: typecheck (`tsc --noEmit`)
- `npm run lint`: biome (lint and format check), then rumdl on Markdown
- `npm test`: vitest
- `npm run check:config-reference`: fails when the generated blocks in
  `docs/config.md` are stale; regenerate with
  `npm run generate:config-reference`
- `npm run bench -- --runs=1 --warmup=0`: benchmark smoke run (see
  `benchmark/README.md`)
- `openspec validate --specs --strict`

Use npm, not bun or pnpm. The package ships `src/` as TypeScript, so there is
no build step. Load a checkout in pi with `pi -e ./src/index.ts`.

## Where things live

- `src/`: runtime. `src/modal/` is the modal engine; `src/vim-editor.ts` is the
  thin pi `CustomEditor` adapter; `src/buffer.ts`, `src/commands.ts` and
  `src/ex.ts` are pure helpers and parsers.
- `openspec/specs/`: durable behavior requirements, the source of truth for
  what the editor does. `openspec/config.yaml` holds the architecture seams
  and design principles. Read the relevant spec before changing behavior.
- `docs/adr/`: architecture decisions, managed with `adrs` in NextGen mode
  (`adrs.toml`).
- `docs/features.md`, `docs/settings.md`, `docs/config.md`: user-facing
  reference docs (ADR-0002). `test/docs-drift.test.ts` matches exact phrases in
  them, so do not reflow them.
- `docs/solutions/`: documented solutions to past problems, with YAML
  frontmatter (`module`, `tags`, `problem_type`). Check it before reworking the
  parser, buffer, modal, or config code. Entries predate the fork and may
  mention Bun commands.
- `CONTEXT.md` (prompt-editing glossary) and `CONCEPTS.md` (input-ownership
  vocabulary): use their terms in specs, tests, and issue titles.
- `docs/rules/`: coding rules; follow them.

## Workflow

- Behavior changes go through OpenSpec: propose with `/opsx-propose`,
  implement with `/opsx-apply`, archive with `/opsx-archive` (prompts and
  skills under `.pi/`, generated by `openspec update`).
- Record durable decisions with `adrs new --tags <tags> "<title>"`. If a change
  contradicts an existing ADR, say so explicitly and supersede it
  (`adrs new --supersedes <n>`) rather than silently diverging.
- Never touch the user's `~/.pi/agent/settings.json` unless explicitly asked.
- When you hit the same error twice, stop and look for alternative fixes
  before trying again.

## Conventions

- Conventional commits (feat, fix, perf, test, docs, style, build, ci, chore),
  imperative mood, lowercase subjects.
- Releases: bump `package.json`, regenerate the lockfile with
  `npm install --package-lock-only` (never hand-edit it), move `[Unreleased]`
  entries in `CHANGELOG.md` under the new version heading, commit as
  `build(release): pi-vimmode vX.Y.Z`, tag `vX.Y.Z`. `:changelog` parses the
  current version's section of `CHANGELOG.md` at runtime, so the heading must
  be `## [X.Y.Z] - YYYY-MM-DD`.
- Issues are tracked in GitHub Issues on `graelo/pi-vimmode`. New PRs use
  `.github/pull_request_template.md`.
